# True Lunar Node Computation

## Background

The Moon's orbital plane is inclined ~5.1 degrees to the ecliptic (the plane of Earth's orbit around the Sun). The two points where the Moon's orbit crosses the ecliptic are called the **lunar nodes** — the ascending (north) node where the Moon crosses going northward, and the descending (south) node 180 degrees opposite.

The ascending node regresses westward around the ecliptic with a period of ~18.6 years. This regression is not uniform: short-period perturbations from the Sun, Jupiter, and Earth's oblateness cause the instantaneous node to oscillate around the smooth "mean" trend by up to ~2 degrees.

## Mean node (Meeus polynomial)

The original implementation in goeph used the Meeus analytical formula — a cubic polynomial in centuries from J2000:

```
Omega = 125.04452 - 1934.136261*T + 0.0020708*T^2 + T^3/450000
```

This gives the **mean** node longitude: a smooth secular trend with no short-period oscillations. It is computationally trivial (no ephemeris needed) but has two limitations:

1. **No short-period perturbations.** The mean node ignores oscillations of up to ~2 degrees that are physically real and relevant for eclipse prediction, astrological computation, and orbit analysis.

2. **Polynomial drift far from J2000.** The cubic polynomial is a fit to the true secular trend near J2000. At the edges of the DE440s range (1850 and 2149, i.e. T = +/-1.5 centuries), the polynomial drifts from the actual secular trend by up to ~2 degrees additional systematic error, because it omits higher-order terms (T^4, T^5, ...).

## True node (r x v algorithm)

The true node is computed directly from the Moon's geocentric state vectors in the SPK ephemeris — no analytical approximations:

1. Get Moon's geocentric position **r** and velocity **v** from DE440s (ICRF frame)
2. Compute orbit normal: **h** = **r** x **v**
3. Normalize: **h_unit** = **h** / |**h**|
4. Define ecliptic pole in ICRF: **k** = (0, -sin(epsilon), cos(epsilon)) where epsilon = 23.4393 degrees (J2000 mean obliquity)
5. Compute node line direction: **n** = **k** x **h_unit** (intersection of orbital and ecliptic planes)
6. Convert **n** to ecliptic longitude via `coord.ICRFToEcliptic()`
7. South node = north node + 180 degrees

This captures the full instantaneous geometry of the Moon's orbit at any moment, including all perturbations encoded in the JPL ephemeris.

### Velocity API

Computing the true node requires the Moon's velocity, not just position. The `spk/` package was extended with:

- `BodyVelocity(body, tdbJD)` — any body's velocity relative to the Solar System Barycenter
- `GeocentricVelocity(body, tdbJD)` — any body's velocity relative to Earth

These are thin wrappers over the existing Chebyshev derivative evaluation (`bodyVelWrtSSB`), following the same layered pattern as the position API.

## Validation challenges

### The self-validation problem

The standard goeph testing approach is to generate golden data in Python/Skyfield and compare Go output against it. For most computations (SPK positions, coordinate transforms, sidereal time, etc.), the Python golden data comes from Skyfield's own functions, which are independently developed and well-tested.

For the true node, no such independent function exists in Skyfield. The initial golden data generator (`generate_true_lunarnodes.py`) implements the same r x v algorithm in Python that goeph implements in Go. This makes the golden test **self-validating** — it can catch language-level bugs (wrong array index, operator precedence) but cannot catch algorithmic errors shared by both implementations.

The same problem exists for the mean node: `golden_lunarnodes.json` is generated by the same Meeus polynomial in Python.

### Comparing true vs mean: hypothesis testing

Since we have two independent computations of the node (true from ephemeris, mean from Meeus), we can validate them against each other by testing physical properties of their difference:

**Near J2000 (20 years, 1-day step):**
- Max |true - mean|: 2.09 degrees (literature predicts ~1.5 degrees for the dominant term; secondary perturbations stack higher)
- RMS: 1.09 degrees
- Mean difference: -0.14 degrees (small residual from incomplete cycle coverage)

**Full DE440s range (300 years, 30-day step, 3653 samples):**
- Max |true - mean|: 3.86 degrees
- RMS: 1.62 degrees
- Mean difference: -0.003 degrees (converges near zero over ~16 full nodal cycles)

The full-range results show the Meeus polynomial drift: all samples where |true - mean| > 2.5 degrees cluster at the date range edges (1850-1945 and 2054-2149). Near J2000, the maximum difference stays within the expected ~2 degree oscillation amplitude. This is documented in the test comments as a failed hypothesis — the initial assumption that |true - mean| < 2.5 degrees everywhere was wrong because the Meeus polynomial itself degrades, not because the true node computation is incorrect.

### Independent validation via Skyfield's osculating elements

The key validation problem remained: how to verify the true node against a genuinely different computation, not just the same algorithm in a different language.

The solution was Skyfield's `osculating_elements_of()` function. This function computes **Keplerian orbital elements** — the six parameters (a, e, i, Omega, omega, nu) that describe an instantaneous elliptical orbit matching the body's current position and velocity. One of these parameters is Omega: the **longitude of ascending node**.

This is the connection: the ascending node we want is exactly what Keplerian element fitting produces as Omega. But the code path is fundamentally different:

**goeph's approach (ICRF throughout):**
1. Compute h = r x v in ICRF
2. Compute n = ecliptic_pole x normalize(h) — node line direction in ICRF
3. Project n onto ecliptic to get longitude

**Skyfield's osculating_elements_of(ECLIPJ2000):**
1. Rotate r, v from ICRF to J2000 ecliptic frame via 3x3 matrix
2. Compute h' = r' x v' in ecliptic frame
3. Extract Omega = atan2(h'[0], -h'[1]) — node longitude directly in ecliptic

Skyfield's implementation uses its own `Distance`, `Velocity`, and `Angle` types, its own `cross()` function from NumPy, and applies the frame rotation before computing any orbital quantities. A bug in goeph's coordinate transform, normalization order, or cross-product operand order would cause disagreement.

**Result:** Agreement at ~4e-11 degrees (~0.1 microarcsecond) across 3653 dates spanning 300 years. This is machine epsilon for float64 arithmetic, confirming the computation is correct.
